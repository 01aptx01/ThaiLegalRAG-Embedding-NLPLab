# ไล่ดูตัวอย่างจากข้อมูลถึงคำตอบ

คู่มือนี้พาอ่านตัวอย่างจริงจากชุดข้อมูลที่โปรเจกต์โหลด ไปจนถึงเวกเตอร์ อันดับค้น และคำตอบที่สร้างจากหลักฐานของแต่ละวิธี จุดประสงค์คือให้ตามกลับได้ว่าคำตอบหนึ่งข้อใช้ข้อมูล รุ่นดัชนี และรายการมาตราใดบ้าง

ในข้อ `pilot-04144` ลองเทียบ Binary BoW กับ TF-IDF ก่อน วิธีแรกพบ `S00755` ในอันดับ 6 จึงอยู่นอกห้าอันดับที่ส่งต่อ ส่วน TF-IDF ส่งมาตรานี้ให้ Typhoon จากอันดับ 3 แต่ช่วงคำตอบที่ได้กล่าวถึงมาตรา 20 ของกฎหมายอีกฉบับ BGE-M3 ให้โมเดลเริ่มตอบจากมาตรา 218/18 ที่ชุดข้อมูลระบุ และคำตอบหยุดกลางประโยคเมื่อครบเพดาน 128 tokens เปิด [รายงานของรอบตัวอย่าง](run/cases.md#pilot-04144)

ในข้อ `test-00016` ทั้งสี่วิธีค้นพบมาตราที่ชุดข้อมูลระบุเป็นอันดับ 1 ช่วงคำตอบของ R1–R3 ใช้พื้นที่ไปกับการทวนคำถามและคัดตัวบท ส่วน R4 ระบุ “สิบสี่วัน” ตรงกับคำตอบอ้างอิงและพาดพิงมาตราอื่นด้วย ตัวอย่างนี้ใช้เทียบความครบของคำตอบและการรองรับจากตัวบททีละข้อ เปิด [ผลข้อทดสอบ](run/cases.md#test-00016)

## เตรียมดัชนีและส่งออกตัวอย่าง

เริ่มจากติดตั้งโปรเจกต์และสร้างดัชนีตาม [คู่มือเริ่มใช้งาน](../getting-started.md) สร้างดัชนีจาก revision เดิมและตั้ง `PYTHONHASHSEED=42` ไว้ก่อน build เมื่อต้องการทำซ้ำตัวอย่างที่สร้างไว้

การส่งออกแบบเต็มต้องใช้ดัชนีที่มีทุกวิธี หากต้องการสร้างคำตอบ ให้เตรียม Typhoon ด้วย revision ที่ตรึงไว้ด้วย สำหรับผู้ที่ยังไม่มี BGE index สามารถเริ่มจากดัชนี R1–R3 ที่สร้างด้วย `--no-dense` แล้วใช้ตัวอย่างย่อย 72 มาตราด้านล่าง

```bash
thai-legal-rag-web build-index --help
python examples/export_walkthrough.py --help
```

คำสั่งแรกแสดงตัวเลือกสำหรับสร้างดัชนี คำสั่งที่สองแสดงตัวเลือกส่งออกตัวอย่าง ตัวอย่างการส่งออกคำถามสองข้อ:

```bash
python examples/export_walkthrough.py \
  --index-dir path/to/index \
  --output-dir path/to/new-example-run \
  --question-id pilot-04144 \
  --question-id test-00016
```

ให้แทน `path/to/index` ด้วยดัชนีที่สร้างไว้ และระบุ `--output-dir` เป็นโฟลเดอร์ใหม่ที่ยังไม่มีอยู่ ต้องระบุ `--question-id` อย่างน้อยหนึ่งครั้งและอาจระบุซ้ำเพื่อเลือกหลายข้อ ตัวอย่างนี้เลือกหนึ่งข้อจาก pilot และอีกข้อจาก test ตัวส่งออกใช้ CPU โดยปริยาย สำหรับดัชนีเต็มที่มี BGE เลือก `--device` ให้ตรงกับอุปกรณ์และชนิดตัวเลขของดัชนี หากต้องการส่งออกรุ่น pilot/test หรือรุ่น Generator ที่กำหนดเอง ให้ใช้ `--pilot-revision`, `--test-revision` หรือ `--generator-revision` ตาม SHA ที่ต้องการทำซ้ำ

### เดโม 4 วิธีค้น โดยไม่ต้องสร้าง BGE index ล่วงหน้า

คำสั่งนี้ใช้ revision เดียวกับรายงานตัวอย่าง เตรียมดัชนี R1–R3 จากคลังเต็ม แล้วคำนวณ BGE-M3 เฉพาะมาตราที่ใช้สาธิต

```bash
PYTHONHASHSEED=42 thai-legal-rag-web build-index \
  --output inference_index --device cpu --no-dense \
  --corpus-revision 069e774f015a50e801dbe2055a29be580c54a83c

python examples/export_walkthrough.py \
  --index-dir inference_index \
  --output-dir path/to/new-subset-run \
  --question-id pilot-04144 \
  --question-id test-00016 \
  --sample-statutes 72 \
  --bge-revision 5617a9f61b028005a4858fdac845db406aefb181 \
  --generator-revision 7513a054da229b9dde7c8cd1a7da57baa36ac59b \
  --generator-bfloat16 --max-new-tokens 128
```

รอบสาธิตใช้ Typhoon แบบ `bfloat16` และให้ตอบได้สูงสุด 128 tokens ต่อวิธี ดู `output_token_limit_reached` เพื่อแยกคำตอบที่ชนเพดานออกจากคำตอบที่จบก่อนเพดาน

สำหรับแต่ละคำถาม ระบบรวม 10 อันดับแรกจาก R1, R2 และ R3 เข้ากับมาตรา gold ทุกข้อ แล้วสุ่มเติมจาก corpus ด้วย seed 42 จนครบ 72 รายการ ชุด 72 รหัสเดียวกันใช้ประเมินทุกวิธีและถูกบันทึกใน `candidate_ids` ของ manifest การ fit R1–R3 รวมถึง vocabulary, IDF และ Word2Vec ยังใช้ corpus เต็ม ส่วนคะแนน retrieval คำนวณบน candidate subset จึงใช้สาธิตวิธีแปลงข้อความและจัดอันดับได้ แต่ใช้แทน benchmark เต็มไม่ได้ หาก candidate จากอันดับค้นและ gold รวมกันเกิน 72 ระบบจะแจ้งข้อผิดพลาด ให้เพิ่มค่า `--sample-statutes` SHA ในคำสั่งตรึง BGE-M3 รุ่นที่ใช้กับตัวอย่างนี้

ใน output directory จะมี `manifest.json`, `dataset.json`, `embeddings.json`, `rankings.json` และ `cases.md` พร้อมโฟลเดอร์ `audit/` ซึ่งมี `audit_scope.json`, `statute_ids.csv`, `question_audit.csv` และ `mapping_audit.csv` ส่วน `duplicate_keys.jsonl` จะมีเมื่อ gold ที่เลือกเกี่ยวข้องกับคีย์ซ้ำ ไฟล์ audit เป็นแถวที่เกี่ยวกับคำถามและ gold ที่เลือก พร้อมตัวอย่างข้อถูกคัดออก ดูขอบเขตไฟล์ใน `audit_scope.json` ส่วน `answers.json` และ `generation/` จะมีเมื่อระบุ `--generator-revision` และโหลดโมเดลได้สำเร็จ

รายงานตัวอย่างที่เช็กอินไว้ใน repository เปิดอ่านได้ที่ [cases.md](run/cases.md) ส่วนคำสั่งด้านบนใช้สร้าง output directory ใหม่เพื่อทำซ้ำจาก index ของเครื่อง

เปิด `manifest.json` ก่อนอ่านตัวอย่าง ที่นั่นระบุรุ่นคลัง รุ่นชุดคำถาม รุ่น BGE-M3 วิธีที่ใช้สร้างดัชนี และคำถามที่ส่งออก หาก SHA หรือรายการวิธีไม่ตรงกับดัชนีและชุดคำถามที่ตั้งใจดู ให้สร้างไฟล์ตัวอย่างใหม่จากรุ่นเดียวกัน

## Session 1 — ข้อมูลต้นทางและการจับคู่มาตรา

ระบบใช้คลังตัวบท `VISAI-AI/nitibench-statute` split `ccl` เป็น corpus ร่วมกันทุกวิธี ส่วนคำถามมาจาก `airesearch/WangchanX-Legal-ThaiCCL-RAG` split `train` (pilot) หรือ `VISAI-AI/nitibench` split `ccl` (test) ตัวอย่างหนึ่งข้อจึงควรแสดงให้เห็นทั้งข้อความดิบจาก dataset และสิ่งที่ระบบนำไปค้น

ใน `dataset.json` ให้ตามจาก `question_id` ไปยังข้อความคำถาม คำตอบอ้างอิง และ `gold_ids` ซึ่งเป็นรหัสมาตราที่จับคู่ได้กับ corpus ตรวจ `law_name`, `section_num` และ `section_content` ของแต่ละรหัสจาก corpus แล้วเทียบกับรายการ `gold_ids` อย่าใช้แค่เลขมาตรา เพราะกฎหมายต่างฉบับอาจมีเลขซ้ำกัน

ข้อความดิบอาจแสดงเลขไทยหรือช่องว่างตามต้นฉบับ ระบบทำสำเนาสำหรับค้นโดยปรับ Unicode เป็น NFC แปลงเลขไทยเป็นเลขอารบิก จัดช่องว่าง และลบอักขระบางชนิดตาม `search_text` ส่วนข้อความตัวบทต้นฉบับยังใช้เป็นหลักฐานที่แสดงให้คนอ่าน การจับคู่มาตราใช้ชื่อกฎหมายกับเลขมาตรา และใช้ข้อความตัวบทช่วยกรณีมีคีย์ซ้ำ ในโฟลเดอร์ตัวอย่าง `audit/` เก็บแถวที่เกี่ยวข้องกับคำถามที่เลือกและตัวอย่างข้อที่ถูกคัดออก ขอบเขตแต่ละไฟล์อยู่ใน `audit_scope.json` หากต้องการ audit ครบทุกแถว ให้รันขั้นเตรียมข้อมูลของโปรเจกต์เพื่อสร้าง audit เต็ม

คำถาม pilot และ test มาจากคนละ split แม้จะถามใกล้เคียงกันก็ควรแสดง split และ revision กำกับไว้เสมอ คู่มือไม่ได้ถือว่าคำถาม pilot เป็นคำถามที่ไม่ซ้ำความหมายกับ test ทั้งหมด โปรแกรมกันคำถามที่ข้อความตรงกันหลังจัดรูป แต่ความซ้ำเชิงความหมายต้องตรวจเพิ่มเติม

## Session 2 — จากข้อความเป็นเวกเตอร์

เปิด `embeddings.json` แล้วเลือกคำถามหนึ่งข้อพร้อมมาตราที่ต้องการเทียบ รูปแบบรายละเอียดต่างกันในแต่ละวิธี เพราะแต่ละวิธีสร้างตัวเลขคนละแบบ

| วิธี | ควรอ่านอะไรในตัวอย่าง | วิธีตีความ |
| --- | --- | --- |
| **R1 · Binary Bag of Words** | คำที่ตัวตัด `newmm` แยกได้ เวกเตอร์แบบพบ/ไม่พบ และตำแหน่งที่มีค่า 1 | ค่าซ้ำในข้อความยังเป็น 1 ช่องหนึ่งแทนคำหนึ่งคำ เวกเตอร์คำถามและตัวบทอยู่ใน vocabulary เดียวกัน |
| **R2 · TF-IDF** | token เดียวกัน, จำนวนครั้งในข้อความ, น้ำหนัก TF-IDF และตำแหน่งค่าน้ำหนักที่ไม่เป็นศูนย์ | คำที่พบบ่อยในข้อความและพบไม่บ่อยใน corpus ได้ค่าน้ำหนักต่างจากคำทั่วไป ค่าในเวกเตอร์ผ่านการปรับความยาวก่อนเทียบ |
| **R3 · Word2Vec Skip-gram** | token ที่โมเดลรู้จักหรือไม่รู้จัก จำนวน token ที่นำมาเฉลี่ย และตัวอย่างพิกัดเวกเตอร์ | โมเดลเรียนรู้เวกเตอร์ของคำจากตัวบท จากนั้นเฉลี่ยเวกเตอร์คำที่รู้จัก คำที่ไม่อยู่ใน vocabulary ไม่มีส่วนในค่าเฉลี่ย |
| **R4 · BGE-M3** | จำนวน token ตาม tokenizer ของโมเดล สถานะถูกตัดตามเพดานหรือไม่ มิติ และพิกัดตัวอย่าง | encoder แปลงข้อความทั้งช่วงเป็นเวกเตอร์หนาแน่น พิกัดเป็นตัวเลขแฝง จึงจับคู่แต่ละพิกัดกับคำเฉพาะไม่ได้ |

R1–R3 ใช้ tokenizer เดียวกันจาก PyThaiNLP `newmm` ส่วน R4 ใช้ tokenizer ของ BGE-M3 พิกัดของ R1–R2 ผูกกับ token ใน vocabulary ส่วนพิกัดของ R3–R4 เป็นมิติที่โมเดลเรียนรู้และไม่มีชื่อ token โดยตรง เวกเตอร์ในตัวอย่างจะแสดงจำนวนมิติจริงพร้อมพิกัดส่วนหนึ่ง

R1 และ R2 ใช้ vocabulary ที่ fit จาก corpus เดียวกันแล้วแปลงคำถามด้วย vectorizer นั้น R3 ใช้ Word2Vec ที่ฝึกจาก corpus ส่วน R4 ใช้ checkpoint ของ BGE-M3 ที่ตรึง revision ใน manifest หากแสดงเวกเตอร์จากดัชนีที่สร้างไว้แล้ว ให้ใช้ไฟล์เมทริกซ์และ model/vectorizer ของดัชนีนั้น อย่าฝึกโมเดลตัวอย่างอีกชุดแล้วอ้างว่าเป็นเวกเตอร์เดียวกับผลอันดับ

## Session 3 — คำนวณ cosine similarity และเรียงอันดับ

ในโปรเจกต์ `rank_exact` รับเวกเตอร์ที่ normalize แล้ว และคูณเวกเตอร์คำถามกับเมทริกซ์ตัวบท ผลคูณจึงเป็น cosine similarity สำหรับทุกมาตรา ระบบเรียงจากคะแนนมากไปน้อยและคืนไม่เกิน `rank_k` รายการ หากคะแนนเสมอกัน ระบบคงลำดับเดิมของรหัสใน corpus ไว้ หากเวกเตอร์คำถามเป็นศูนย์ ระบบคืนรายการว่าง

ลองคำนวณด้วยมือจากเวกเตอร์สมมติ 3 มิติ ให้คำถามเป็น `q = (1, 1, 0)` และตัวบทเป็น `A = (1, 1, 0)`, `B = (1, 0, 1)`, `C = (0, 1, 0)` เมื่อ normalize แล้ว cosine เท่ากับผลคูณจุด

| ตัวบทตัวอย่าง | cosine กับ q | อันดับ |
| --- | ---: | ---: |
| A | 1.000 | 1 |
| C | 0.707 | 2 |
| B | 0.500 | 3 |

ดังนั้นลำดับจากคะแนนสูงไปต่ำคือ `A, C, B` ในผลจริงแต่ละแถวของ `rankings.json` แสดงรหัสมาตรา อันดับ คะแนน cosine และป้าย gold ระบบคำนวณกับทุกมาตราในขอบเขตที่ระบุใน manifest ก่อนเก็บรายการตามค่า `rank_k`

คะแนนจากคนละวิธีไม่ได้อยู่บนสเกลที่ควรนำมาเทียบตรง ๆ เช่น cosine 0.7 ของ TF-IDF ไม่ได้แปลว่ามั่นใจเท่ากับ 0.7 ของ BGE-M3 ให้เทียบลำดับของมาตราและคะแนน retrieval โดยคงคำถามกับขอบเขต candidate เดียวกัน ผล subset กับผล full corpus ต้องแยกขอบเขตกัน

## Session 4 — คำตอบจากหลักฐานที่แต่ละวิธีค้นพบ

ถ้าเปิดการสร้างคำตอบ `answers.json` จะมีคำตอบของคำถามเดียวกันจากบริบทที่ได้จากแต่ละ retrieval method โมเดล คำสั่งสร้างคำตอบ ค่า token limit และรุ่นโมเดลควรเหมือนกันในรอบเทียบนี้ ความต่างที่ตั้งใจดูคือชุดมาตราที่ค้นได้

ระบบเก็บผลค้นสูงสุด `rank_k=10` รายการใน `rankings.json` ฟิลด์ `retrieved_ids` จึงหมายถึงรายการผลค้นที่เก็บไว้ ส่วนตอนสร้างคำตอบจะพิจารณาเฉพาะ 5 อันดับแรกตาม `top_k=5` ใน manifest แล้วบันทึกเป็น `top_k_ids` ใน `answers.json` รายการที่เข้า prompt จริงอาจมีน้อยกว่านี้

อ่านแต่ละคำตอบตามลำดับนี้:

1. ดู `top_k_ids` เพื่อเห็น 5 อันดับแรกที่ใช้เป็นบริบทตั้งต้นตอนสร้างคำตอบ
2. ตรวจ `prompt_ids` ว่ามาตราใดถูกใส่ใน prompt จริง
3. ตรวจ `omitted_ids` ว่ามาตราใดอยู่ใน top-k แต่ไม่ได้ถูกใส่เนื่องจากงบ token
4. อ่านข้อความคำตอบเทียบกับ `reference_answer` และตัวบทฉบับเต็มจาก corpus
5. ตรวจ `cited_ids` กับ `invalid_ids` เพื่อดูว่ารหัสอ้างอิงอยู่ในหลักฐานที่ส่งให้โมเดลหรือไม่

`gold_in_prompt` บอกว่ามีมาตราอ้างอิงอย่างน้อยหนึ่งรายการอยู่ใน prompt ส่วน `context_recall` บอกสัดส่วนมาตราอ้างอิงที่เข้า prompt ใช้ `invalid_ids` ตรวจว่ามีรหัสอ้างถึงมาตราที่ไม่ได้ส่งให้โมเดลหรือไม่

`abstained` นับกรณีที่คำตอบขึ้นต้นด้วย “หลักฐานไม่เพียงพอ” ตรงตามรูปแบบที่โปรแกรมตรวจ ในผล Word2Vec ของ `pilot-04144` ข้อความดังกล่าวอยู่หลังการทวนคำถาม จึงเห็นประโยคนี้ในคำตอบแม้ค่า `abstained` เป็น `0`

## Session 5 — ตัวชี้วัดกับการตรวจโดยคน

`rankings.json` ใช้ดูอันดับรายข้อ ส่วน summary ของรอบเต็มช่วยสรุปหลายคำถาม:

| ตัวชี้วัด | อ่านความหมาย |
| --- | --- |
| Recall@k | สัดส่วนมาตราอ้างอิงที่พบใน k อันดับแรก |
| Hit@k | พบมาตราอ้างอิงอย่างน้อยหนึ่งรายการใน k อันดับแรกหรือไม่ |
| nDCG@k | ให้น้ำหนักมากกว่าแก่การพบมาตราอ้างอิงในอันดับต้น ๆ และปรับเทียบกับอันดับที่ดีที่สุดที่เป็นไปได้ |
| MRR@k | ค่าเฉลี่ย reciprocal ของอันดับแรกที่พบมาตราอ้างอิง ภายใน k อันดับ |

คะแนน retrieval ใช้มาตราที่ชุดข้อมูลกำหนดเป็น gold วัดว่าค้นพบมาตราเหล่านั้นได้ดีเพียงใด

คุณภาพคำตอบต้องตรวจแยกจากคะแนน retrieval ใช้แบบฟอร์ม `review_template.csv` ของรอบทดลอง แล้วอ่านคำตอบเทียบกับคำตอบอ้างอิงและตัวบท ให้ผู้ตรวจกรอก `coverage`, `contradiction` และ `citation_support` ตาม [คู่มือการประเมิน](../evaluation.md) การตรวจรูปแบบรหัส citation อย่างเดียวไม่ยืนยันว่าเนื้อหาคำตอบถูกต้อง

## ไฟล์ที่สร้างและการอ่านย้อนกลับ

| ไฟล์ | ใช้ดูอะไร |
| --- | --- |
| `manifest.json` | รุ่นข้อมูล/โมเดล วิธีค้น อุปกรณ์ และรหัสคำถามที่ส่งออก |
| `dataset.json` | แถวคำถามที่เลือก คำตอบอ้างอิง รหัส gold และตัวบทที่จับคู่ได้ |
| `embeddings.json` | tokenization หรือรายละเอียดเวกเตอร์ที่อธิบายการแทนข้อความในแต่ละวิธี |
| `rankings.json` | คะแนน cosine และลำดับผลค้นของแต่ละวิธีสำหรับคำถามเดียวกัน |
| `answers.json` | คำตอบพร้อม prompt IDs, omitted IDs และ citation trace เมื่อเปิด generator |
| `cases.md` | หน้ารวมตัวอย่างสำหรับอ่านตั้งแต่คำถามถึงคำตอบ |
| `audit/audit_scope.json` | ระบุแถวที่เก็บไว้ในไฟล์ audit แบบย่อ |

ไฟล์ตัวอย่างตั้งใจให้เล็กพอสำหรับอ่านและแสดงที่มาได้ เปิดดัชนีและไฟล์ที่สร้างจากแหล่งที่ไว้ใจได้เท่านั้น โดยเฉพาะไฟล์ `joblib` ในดัชนี เพราะการโหลดไฟล์ pickle จากผู้ส่งที่ไม่รู้จักอาจเรียกใช้โค้ดได้ ดูข้อกำหนดของชุดข้อมูลและโมเดลที่ [คู่มือข้อมูล](../data.md) และ [คู่มือ retrieval](../retrieval.md)
